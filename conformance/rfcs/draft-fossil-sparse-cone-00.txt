      The Fossil Distributed Version Control System: Sparse Cones
                      draft-fossil-sparse-cone-00

Abstract

   This document specifies sparse cones for repositories following the
   Fossil artifact model: a mechanism by which a checkout materializes,
   and optionally a repository stores, only a declared subset of a
   check-in's file tree.  It defines two independent capabilities.  The
   sparse worktree (full store, partial materialization) is available to
   any conforming repository.  The sparse store (deliberately partial
   artifact holdings) requires sub-manifest tree structure, because a
   flat check-in manifest is a single artifact that cannot be partially
   held, while sub-manifest subtrees are separate artifacts that can be
   held as deliberate phantoms yet remain referencable by hash at commit
   time.  The design rests on the observation that sub-manifest
   partitioning produces leaves that are contiguous ranges of the sorted
   path list, so a directory cone intersects a number of tree nodes
   proportional to the cone rather than to the repository.

1.  Introduction

1.1.  Two Problems, Usually Conflated

   A participant in a large multi-project repository wants two different
   things.  First, a sparse worktree: do not materialize the subtrees of
   other projects.  Storage is complete; the working directory and the
   tracking surface are partial.  Second, a sparse store: do not
   transfer or hold the artifacts of other projects.  The local artifact
   set is deliberately incomplete.

   These fail differently, cost differently, and have different
   structural prerequisites.  This document keeps them separate
   throughout: the sparse worktree is specified in Section 4 and the
   sparse store in Section 5.

1.2.  Why Flat Manifests Cannot Yield a Sparse Store

   The unit of storage and synchronization is the artifact, named by the
   cryptographic hash of its content [FossilArtifact].  A flat check-in
   manifest is one artifact carrying the entire file list.  An artifact
   is either held or phantom; it cannot be partially held.  History
   traversal requires every check-in's manifest, so a store holding flat
   manifests must hold the complete file-list history of the whole
   repository regardless of the consumer's interest.

   File-content blobs were never the obstacle.  The phantom state
   [FossilRepoState] already lets a store know an artifact by name
   without holding its content, and shunning already exercises permanent
   holes.  The atom is wrong-sized at exactly one place: the manifest.

   Sub-manifests [FossilSubManifests] correct the atom.  With S-card
   trees the check-in manifest is a small spine and subtrees are
   separate artifacts.  Separate artifacts can be phantoms.  That is the
   entire structural unlock; everything in Section 5 follows from it.

1.3.  The Contiguity Property

   Section 6.2 of [FossilSubManifests] partitions the sorted F-card
   list, placing group boundaries where a key's hash reaches the
   height's zero-bit threshold.  Every leaf is therefore a contiguous
   range of sorted paths.  Sorted paths have directory-prefix locality:
   all files under a common directory prefix are adjacent.  A directory
   cone is consequently a contiguous key interval, and the set of tree
   nodes whose key range intersects it has size proportional to the cone
   plus the spine.  This is the same property that directory-aligned

   tree objects give other version control systems, arrived at from a
   balance-first construction.

   This document introduces no new partitioning; it consumes the
   existing one.

2.  Terminology

   Cone:  A finite set of repository-relative path prefixes, each naming
      a directory subtree or a single file.  The cone covers a path if
      any member is a prefix of it under slash-component semantics.  The
      empty cone covers nothing; the absent cone covers everything
      (dense operation, the behavior of implementations predating this
      document).

   In-cone, out-of-cone:  A path, F card, blob, or sub-manifest node
      classified by cone coverage.  A sub-manifest node is in-cone if
      its key range intersects any cone member's interval.

   Spine:  The check-in manifest artifact itself plus every interior
      sub-manifest node on a path from it to an in-cone leaf.

   Elided phantom:  A phantom whose absence is the deliberate result of
      local cone policy (Section 5.2), as distinct from a transit
      phantom (content not yet arrived) and a shunned artifact (content
      forbidden).

   Dense:  The absence of sparseness.  A dense checkout or store behaves
      exactly as specified by the base documents.

3.  The Cone Specification

3.1.  Location and Mutability

   A worktree cone is checkout-local state, recorded with the checkout's
   other authoritative local records.  A store cone is store-adjacent
   local state.  Neither is an artifact; neither synchronizes; neither
   affects any artifact's bytes or name.  Two clones of one repository
   MAY hold different cones.  A cone MAY be widened or narrowed at any
   time (Section 5.4).



Mestas                    Expires 22 April 2027                 [Page 4]

Internet-Draft             Fossil Sparse Cones              October 2026


   A cone MAY carry members of kinds other than path prefixes, each
   defined by another document; the horizon member of draft-fossil-
   horizon is one.  The canonical serialization MUST mark a cone
   carrying any such member with a version distinct from that of a cone
   carrying only path members, and an implementation that does not
   understand the version MUST refuse the cone rather than read it as
   path members.  Refusal is policy loss (Section 5.2): the store heals
   toward dense.

3.2.  Normalization

   Implementations MUST normalize cone members through the same
   worktree-path validation applied to tracked paths (no dot or dot-dot
   components, no empty components, no reserved roots) and MUST remove
   members covered by another member of the same polarity with no
   opposite-polarity member between them (for a cone with no exclusions
   this is simply: covered by another member).  The normalized cone is
   what all classification uses.

   Implementations MUST support at least 64 members and SHOULD support
   255 -- scattered-file profiles (individual root files beside
   directory subtrees) are first-class, not an abuse of the mechanism.

3.3.  Exclusions

   A cone MAY carry exclusion members: paths subtracted from the
   coverage of an inclusion member, expressing "this subtree, except
   that part of it".  Coverage is decided by the most specific matching
   member: the longest member, of either polarity, that covers the path.
   Because members are plain path prefixes, any two members covering one
   path are nested, so this is exactly the last-match-wins discipline
   ignore files made familiar, under the natural ordering -- but stated
   over member length it is order-independent, so the canonical sorted
   serialization and the digest survive unchanged.  Polarity MAY
   alternate along a nesting chain: a subtree excluded from an inclusion
   may itself contain a deeper re-inclusion.

   Normalization extends to polarity: a member whose nearest covering
   member has the same polarity is redundant and MUST be removed; an
   exclusion no inclusion covers is a dead rule and MUST be refused --
   it can only be operator error; one path carried with both polarities
   is a contradiction and MUST be refused.

   Exclusions narrow the contiguity property rather than break it: a key
   range wholly inside an inclusion and wholly outside every exclusion
   classifies as before; a range an exclusion intersects is classified
   per file.  The cost falls on the boundary, never on correctness.

3.4.  Literal Prefixes Only

   Members are literal path prefixes.  Pattern members (globs, character
   classes, suffix matches) are not part of this document: every
   efficiency claim herein -- sub-manifest range pruning (Section 1.3),
   server-side interval classification (Section 6.2) -- rests on a
   member denoting one contiguous key interval under sorted-path order,
   and a pattern denotes scattered intervals, degrading every
   classification to a full scan.  An implementation wanting patterns
   would be defining a different, slower mechanism, and should say so
   rather than extend this one.  A metacharacter in a member is a
   literal character of the path: an implementation MUST NOT expand it,
   and MAY refuse the member.

   A member names a directory subtree or a single file with equal
   standing: file members are how a profile picks individual files
   without adopting their directories.

3.5.  Amendment

   Editing a cone by wholesale replacement and editing it by member
   addition or removal are equivalent; an implementation SHOULD offer
   the incremental form, because restating a large member set to change
   one entry is the kind of friction that pushes operators back to dense
   clones.  Widening triggers the demand-fetch of Section 6.4 (policy
   form); narrowing dematerializes and leaves reclamation to explicit
   compaction (Section 5.4).

4.  The Sparse Worktree

   The sparse worktree is available to any conforming repository,
   whether its manifests are flat or tree-structured.  On flat manifests
   it is purely algorithmic; its costs are stated in Section 4.5.

4.1.  Materialization and Tracking

   A checkout operation given a cone MUST materialize exactly the
   covered files.  The managed-file record covers only in-cone files.
   Status, untracked-file listing, and bulk tracking operations operate
   within the cone; an uncovered on-disk path is neither reported as
   untracked nor eligible for tracking.  An implementation MUST refuse a
   request to track a path outside the cone and the refusal MUST name
   the cone as the reason.  A diagnostic that merely reports a missing
   file, or alleges damage, does not conform.







Mestas                    Expires 22 April 2027                 [Page 6]

Internet-Draft             Fossil Sparse Cones              October 2026


   All file-set enumeration flows through the shared enumeration
   interface required by Section 9.3 of [FossilSubManifests], with the
   cone applied as a range predicate at that interface.  Implementations
   MUST NOT filter at individual call sites; the single filter point is
   what keeps every verb consistent.

4.2.  Commit Synthesis

   A commit from a sparse worktree MUST produce a check-in whose file
   set is the union of the in-cone files as observed in the worktree and
   the baseline check-in's out-of-cone entries carried unchanged.

   For flat manifests, the implementation copies the baseline's out-of-
   cone F cards byte-verbatim into the new manifest, merged in sorted
   order with the in-cone F cards.

   For tree manifests, the implementation MUST produce the canonical
   construction of Section 6.2 of [FossilSubManifests] under the
   requested partition parameter k.  It MAY re-reference a parent
   subtree by hash without its content only when it has established that
   the subtree is byte-identical to the full construction's result.

   The structural affected range is not limited to ranges intersecting
   changed paths.  Insertions, deletions, and renames can shift MAX cuts
   or change MIN and final-small-group merges; the resulting node keys
   and group boundaries can propagate at every height.  There is no
   fixed rewrite or fetch radius: a MAX-cut shift can traverse a long
   suffix before the old and new constructions re-synchronize.  Out-of-
   cone file entries remain unchanged even when the nodes carrying them
   must change.

   An edit preserving the filename set preserves its partition only if
   the parent's applicable partition basis is established.  The mutable
   current k is not evidence of the parent's construction k, which is
   not encoded in artifacts.  Before opaque reuse, the writer MUST
   either verify the relevant partition under the requested k from the
   descriptors and entries needed by the construction, or use trusted
   local derivation evidence bound to the immutable parent identity,
   construction rules, and k.  Unknown or different parent k requires
   validation or reconstruction under the requested k, fetching any
   necessary nodes; it MUST NOT be treated as an unchecked caller
   precondition.

Internet-Draft             Fossil Sparse Cones              October 2026


   When construction or validation needs an absent adjacent node, the
   writer MUST resolve it through Section 6.4 or refuse explicitly
   without publishing a partial check-in.  It MUST NOT silently splice
   noncanonical nodes or substitute empty entries for absent content.
   Subtrees proved unchanged outside the complete structural affected
   range can remain elided.

   The result is an ordinary check-in.  A reader cannot detect that it
   was committed sparsely, and this document introduces no new artifact
   form.

4.3.  The R Card

   The R card is a checksum over the complete file contents of a check-
   in [FossilArtifact] and is not composable from partial content.  A
   sparse-worktree commit over a dense store MAY compute the R card by
   reading out-of-cone content from the store.  A commit over a sparse
   store (Section 5) MUST omit the R card; omission is already
   conforming.  Verifiers MUST NOT treat an absent R card as damage.

   The verification side is the same rule reflected: a checkout-side
   verifier checking a PRESENT R card during a sparse materialization
   MUST compute the aggregate over the dense enumeration, reading out-
   of-cone content from the store -- over a dense store the cone narrows
   materialization and never weakens R verification.  A verifier over a
   sparse store cannot compute the aggregate and MUST skip R
   verification rather than report disagreement; elided content makes
   the card unverifiable, not wrong.

4.4.  Operations That Cross the Cone

   Merge, update, and revert operations MAY need to apply changes to
   out-of-cone files.  Over a dense store the implementation MUST apply
   such changes to the record (manifest synthesis) without materializing
   the files, and SHOULD report the count of out-of-cone changes
   applied.  Read operations on an uncovered path over a dense store
   read the store; the cone governs materialization, not readability.

4.5.  Cost Properties

   This section is informative.  On flat manifests every commit still
   writes, and every derivation still parses, file lists proportional to
   repository width.  The sparse worktree saves disk, status time, and
   materialization time; it does not touch the manifest cost.  On tree
   manifests, reads confined to covered ranges can cost the order of the
   cone plus the spine.  A commit additionally pays for its complete
   structural affected range and for establishing the applicable
   partition basis (Section 4.2); neither cost has a fixed cone-local

   bound.  Tree manifests permit the sparse store of Section 5, while a
   flat manifest must itself remain dense.

5.  The Sparse Store

   A sparse store REQUIRES tree manifests for the repository segment
   being elided.  A repository whose history contains a flat segment MAY
   elide only that segment's content blobs; its flat manifests MUST be
   held densely (Section 5.5).

5.1.  Holdings

   A store sparse at cone C holds, for every check-in: the manifest
   artifact; every in-cone sub-manifest node; and every blob referenced
   by an in-cone F card.  Out-of-cone sub-manifest nodes and blobs MAY
   be absent, represented as elided phantoms; already-held or demand-
   fetched payloads need not be discarded.  It holds all non-manifest
   structural artifacts (control, wiki, ticket, event, forum,
   attachment) densely: they are small, and holes in non-file surfaces
   would surprise every consumer that renders them.

5.2.  The Third Phantom Class

   Implementations MUST distinguish three absence classes:

   1.  Transit phantom: wanted, not yet arrived; synchronization
       requests it.

   2.  Shunned: forbidden; never requested [FossilRepoState].

   3.  Elided phantom: deliberately absent under local cone policy.
       Synchronization MUST NOT spontaneously request it, and its
       absence is healthy.


















Mestas                    Expires 22 April 2027                 [Page 9]

Internet-Draft             Fossil Sparse Cones              October 2026


   Elision is a local classification computed over the cone
   specification, not a stored mark on the phantom record;
   reclassification on cone change is recomputation, not migration.  A
   consequence implementations SHOULD preserve: loss of the store-cone
   specification reclassifies every elided phantom as a transit phantom,
   and the store then heals toward dense through ordinary
   synchronization.  Policy loss is never damage and never data loss; it
   costs bandwidth.  Storing the cone with the disposable derived-state
   tier is therefore sound and RECOMMENDED.  A verification operation
   MUST report a store that is complete within its cone as healthy, MUST
   report elision counts distinctly from damage, and MUST continue to
   report transit phantoms and damaged in-cone artifacts exactly as for
   a dense store.  The failure mode this rule prevents: an operator
   conditioned to expect thousands of "missing" artifacts stops reading
   verification output.

5.3.  Commit, Synchronization, and Correctness with Elided Subtrees

   Commit operates per Section 4.2: out-of-cone subtrees proved
   identical to the canonical result may be referenced by hash without
   possession, but nodes needed for canonical boundary propagation or
   partition validation MUST be fetched through Section 6.4 or the
   commit refused.  The holdings above are therefore a coverage policy,
   not a promise that every commit can complete using only those
   holdings.  Pushing a completed check-in is sound: the receiving peer
   either holds the referenced subtrees (a dense peer, or a peer with an
   overlapping cone) or creates transit phantoms and requests them from
   peers that hold them, which is ordinary convergence [FossilSync].  A
   sparse store can therefore be a first-class committing, pushing, and
   pulling participant.

   What a sparse store cannot be is a complete origin.  A dense peer
   cloning from a sparse store receives elided phantoms it must resolve
   elsewhere.  A server SHOULD refuse to act as a clone origin for cones
   it does not cover unless explicitly configured as a partial mirror.
   The refusal is one error card and no content.  A requesting client
   MUST treat a clone-round reply that carries an error card and no
   clone progress as fatal, the error-card tolerance of [FossilSync]
   notwithstanding: that tolerance exists for cosmetic cards riding an
   otherwise-progressing reply, and honoring it here would let a refused
   clone terminate empty and report success.

5.4.  Widening and Narrowing

   Widening the cone reclassifies the newly covered elided phantoms as
   transit phantoms and fetches them (Section 6.4).  Narrowing
   reclassifies in the other direction and MUST NOT by itself delete
   content already held.  Deletion occurs only through explicit
   compaction, which drops artifacts that are both out-of-cone and
   unreferenced by any spine, and which rides the existing store-rewrite
   machinery and its exclusion locks.  Compaction after narrowing is the
   only deletion in this document.

5.5.  Hybrid Histories

   Disabling or enabling sub-manifest emission cannot rewrite stored
   artifacts, so a repository that adopted sub-manifests after its
   creation has a permanently flat prefix ([FossilSubManifests],
   Section 8.1).  The flat prefix's manifests are unsplittable and MUST
   be held densely; its content blobs MAY be elided by F-card
   classification.  A repository converted wholesale to tree manifests
   (a rebirth that re-mints history under new names) has no flat segment
   and sparsifies fully.

6.  Sync Protocol Extension

6.1.  The Cone Pragma

   A cone-scoped pull or clone request adds one pragma card per cone
   member:

   pragma cone <member>

   carried in the request body alongside the operation's existing cards,
   with each member encoded exactly as an F-card filename.  The pragma
   mechanism is chosen deliberately: the reference implementation's
   transfer processor answers an UNRECOGNIZED bare card with a protocol
   error ("error bad command"), while pragmas are specified as requests
   only, with unknown pragmas silently ignored.  Riding the pragma is
   therefore what makes the degradation of Section 6.3 a documented
   property of the reference implementation rather than an assumption
   about its tolerance.

   An exclusion member travels as its own pragma:

   pragma cone-not <member>







Mestas                    Expires 22 April 2027                [Page 11]

Internet-Draft             Fossil Sparse Cones              October 2026


   A distinct pragma name rather than a prefix character, because every
   byte that could mark a member as negative is also a legal filename
   byte.  A server understanding cone but not cone-not would over-send;
   the requester's local filtering (Section 6.3) absorbs the surplus, so
   partial understanding degrades exactly as no understanding does.

   The collected members form the request's cone.  Its semantics: for
   check-in content, send spines, in-cone sub-manifest nodes, and in-
   cone blobs; do not send, and do not expect the requester to request,
   the remainder.

6.2.  Server Behavior

   A cone-aware server walks each check-in's tree, descending only nodes
   whose key range intersects the cone (the single-name lookup of
   [FossilSubManifests] Section 5.3 generalized to intervals), and emits
   the spine, the in-cone nodes, and the in-cone blobs.  Deciding key
   ranges requires plaintext; the send-gate of [FossilSubManifests]
   Section 7.2 already establishes inflation on the serve path.  A
   server MUST bound the per-round walk exactly as a dense clone bounds
   its batches.

   A stored artifact may be held as a delta against a base, and a dense
   reply serves such a container verbatim because a dense recipient
   holds the base.  A cone-scoped recipient may not: a kept blob whose
   base is out-of-cone would arrive as a delta whose source the
   recipient's own policy elides and never requests (Section 5.2), a
   blob it holds the bytes of and can never materialize.  A cone-aware
   server MUST NOT serve a delta whose base is outside the keep set it
   computed for the request; it serves that artifact in full form.  The
   test is a keep-set lookup per served delta; reconstruction is paid
   only for the deltas that cross.  A recipient MUST treat a phantom
   that a retained delta names as its source as a transit phantom
   whatever its cone classification, so that a server predating this
   rule costs bandwidth and never a stuck artifact.

6.3.  Graceful Degradation

   A cone-ignorant server silently ignores the unknown pragma -- the
   pragma contract of the reference implementation -- and serves
   densely.  The requester MUST then filter locally: store in-cone
   artifacts, record elided phantoms for the remainder, and report the
   counts.  Nothing is discarded silently.  Correctness is therefore
   preserved against every peer; only bandwidth is lost against a cone-
   ignorant one.  A cone-aware server SHOULD advertise the capability so
   clients can report which mode a transfer used.

6.4.  Demand Fetch

   An operation over a sparse store that crosses the cone (a merge
   needing an out-of-cone blob, an annotation of an uncovered path, a
   checkout after widening, or a commit needing adjacent sub-manifests
   for canonical construction or partition validation) resolves elided
   phantoms by either of two conforming forms.  The targeted form issues
   a request naming the exact artifacts: the existing request machinery
   scoped to an explicit set.  The policy form -- RECOMMENDED when the
   crossing expresses a lasting intent, as a widened checkout does --
   updates the store cone to the requested coverage and performs an
   ordinary cone-scoped synchronization: suppression and receive
   filtering then align with the new policy with no special-case
   transfer path, and any content the peer lacked remains a transit
   phantom that later synchronization heals (Section 5.2's loss rule,
   applied deliberately).  With no configured peer to fetch from, the
   operation MUST refuse and the diagnostic MUST name the class (the
   count of artifacts elided by the sparse cone, and the absence of a
   peer) and MUST NOT describe the condition as missing or corrupt.  If
   a configured peer cannot supply required content, the operation MUST
   refuse with an explicit diagnostic identifying the unavailable
   content; it MUST NOT report success with an incomplete
   reconstruction.

6.5.  Not an Authorization Boundary

   The cone is bandwidth and locality policy, not access control.
   Possession of a spine hash permits requesting the corresponding
   subtree from any peer that holds it.  Path-level authorization
   requires server-side access control evaluated on the serve path and
   is out of scope for this document, whose only obligation is to state
   plainly that sparseness provides none.

7.  Interactions

   This section is informative.

   Derived caches: a derivation cache and any prefix-anchored checkpoint
   derive over the log's bytes, and the cone never alters stored bytes
   -- elision is computed at read time (Section 5.2), never folded into
   the derived record.  The record is therefore cone-independent BY
   DESIGN, and cache keys MUST NOT incorporate the cone: doing so
   converts every cone change into a full re-derivation that corrects
   nothing.  The one operation that does alter bytes, compaction after
   narrowing (Section 5.4), rewrites the log and thereby misses every
   prefix-anchored cache through the existing prefix-identity
   validation, with no cone term needed.

   Enumeration: the cone predicate lands once, at the shared enumeration
   interface, and every consumer inherits it.

   Checkout state: the worktree cone is a new section of the checkout's
   container record and should ship in the same container revision as
   other pending additions, so the format is bumped once.

   Adoption analysis: sparse capability is a benefit of sub-manifest
   adoption that byte-cost replay tables cannot express.  Tooling that
   advises on adoption should mention it qualitatively when refusing on
   byte costs alone.

8.  Security Considerations

   The non-guarantee of Section 6.5 is the principal consideration:
   sparseness is not an authorization mechanism, and deployments
   requiring path-level secrecy need server-side access control
   independent of this document.

   The cone card enlarges the request-parse surface.  Member count and
   member length MUST be bounded with the same limits applied to F-card
   filenames.

   The server-side tree walk on cone requests MUST carry the same depth
   and visited-node bounds as single-name lookup ([FossilSubManifests],
   Section 10); without them a crafted cone converts an unauthenticated
   request into an amplification primitive.

   Demand fetch discloses to the serving peer exactly which paths a
   sparse client is interested in.  Hosted deployments should treat cone
   contents as information about their users.

   This revision of draft-fossil-sparse-cone-00, dated 20 October 2026,
   applies the following corrections to the 14 August 2026 text.

   *  Section 3.1: a cone MAY carry members of kinds other than path
      prefixes; a cone carrying one is serialized under a distinct
      version, and an implementation that does not understand the
      version refuses the cone, which is policy loss (Section 5.2).
      Normative change.

   *  Section 3.2, Section 3.4, Section 3.6: Section 3.6 is removed and
      Section 3.4 is the one statement of literal prefixes, with an
      unconditional rule for metacharacters; the member-count
      requirement appears once, in Section 3.2; Section 3.3 alone
      governs exclusions.  Normative change.

   *  Section 6.2: a cone-aware server serves in full form any artifact
      whose delta base lies outside the keep set it computed for the
      request, and a recipient treats a phantom that a retained delta
      names as its source as a transit phantom.  Normative change.

   *  Section 4.2, Section 4.5, Section 5, Section 6.4: canonical
      construction takes precedence over path-local reuse.  Define
      structural boundary propagation, require evidence of a compatible
      parent partition before opaque reuse, and require demand fetch or
