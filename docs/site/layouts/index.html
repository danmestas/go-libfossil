A Fossil repository engine that compiles to WebAssembly.

go-libfossil reads, writes and syncs Fossil repositories: the artifact format, the derived tables and the sync protocol, in Go without cgo. The same engine runs as a command-line tool, inside a server, in a browser tab, or inside a storage object at the edge.

Where it runs

Version control inside the application, not beside it.

The repository is a SQLite database with Fossil's own tables, so wherever SQLite runs, so does the repository. A database/sql driver is the only thing a new host has to supply.

Server and CLI

One static binary

The libfossil command and the Go API build to a single binary for Linux, macOS and Windows, with no fossil installation and no C toolchain.

Serve repositories, mirror them, or read history from a build pipeline through typed Go values instead of parsed command output.

Browser

A repository in the page

Built for js/wasm with the ncruces SQLite driver, which ships SQLite itself as WebAssembly. A page holds a whole repository and syncs it with a server when it chooses to.

A document that explains a protocol can let its reader commit, branch, merge and sync in the page, and watch the tables change.

Edge storage

History next to the data

Built with TinyGo, the whole API fits inside a storage object that runs its own SQLite. Each request is one call into the engine inside one transaction, so it completes or leaves nothing behind.

A publishing tool can keep every revision of what it publishes as Fossil check-ins in the object that serves it, and show the history without a separate service.

Checked against the specification, requirement by requirement.

Against the real implementations

Interop tests run the fossil {{ $fossil }} binary and zit against go-libfossil in both directions: each clones, pulls and pushes the other's repositories, and each verifies what it received.

Deterministic simulation

Sync is also run in a seeded simulation that drops requests, truncates replies and partitions nodes. After each run it checks blob integrity, delta chains and convergence. Any failure replays exactly from its seed. The repository also carries {{ lower (index $words (string $facts.fuzzTargets) | default (string $facts.fuzzTargets)) }} fuzz targets.

Partial history

Hold the history you need.

A repository does not have to hold everything. A cone keeps the content of chosen paths. A horizon keeps history from a chosen check-in forward and leaves the rest on the origin, fetched only when an operation needs it. At the structural depth the clone also drops the manifests below the horizon and derives branch and tag state from a seed the origin signs.

A structural clone of fossil-scm.org's repository, 21,008 check-ins, takes about 30 seconds. How horizons work.

Start

Open a repository and commit.

From the command line, or from Go. The libfossil command drives the same code as the library, and the file it writes is an ordinary Fossil repository: stock fossil reads it.

What it is not
  • Not a replacement for the fossil binary's web interface, wiki or forum server.
  • Not a hosting service: it is a library and a command-line tool you run.
  • Not a Git bridge. It speaks Fossil's formats and protocol only.
